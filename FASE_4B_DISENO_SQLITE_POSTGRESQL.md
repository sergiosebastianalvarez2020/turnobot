# FASE 4B — DISEÑO TÉCNICO SQLITE → POSTGRESQL (REVISIÓN 4B.1)

## A. Resumen ejecutivo

TurnoGo actualmente opera sobre SQLite 3 en modo WAL con un esquema de 22 migraciones. El sistema es una aplicación Flask / Waitress servida detrás de Nginx, multi-tenant por `business_id` derivado del slug de la URL, con concurrencia controlada por `BEGIN IMMEDIATE` + índices únicos parciales. La base de datos de producción en OCI contiene 1 negocio, 21 turnos y 1 usuario (385 KB).

La migración a PostgreSQL busca eliminar el cuello de botella del single-writer de SQLite, permitir conexiones concurrentes reales, garantizar atomicidad en reservas y escalar horizontalmente. El diseño propuesto:

1. **Connection Pool**: `psycopg3` (`psycopg_pool.ConnectionPool`) con pool por proceso Waitress, configurado exclusivamente mediante `DATABASE_URL` (DSN estándar libpq).
2. **Schema & Identidad**: Identidad de tablas preservada. IDs enteros secuenciales preservados durante la migración mediante `GENERATED BY DEFAULT AS IDENTITY`. Secuencias reiniciadas post-migración.
3. **Tipos de Datos**: Mapping conservador y preciso. `INTEGER` → `INTEGER`, `TEXT` → `TEXT`, `REAL` (precios) → `NUMERIC(10,2)` (pesos con centavos), booleanos-like → `BOOLEAN`, timestamps → `TIMESTAMPTZ` (UTC).
4. **datetime('now') & Timestamps**: SQLite `datetime('now')` genera ISO-8601 en **UTC** (no hora local del servidor). Se reemplaza por `NOW()` en la base PostgreSQL y se preserva `datetime.now(UTC)` en Python para timestamps del sistema. Las fechas y horas de negocio (`appointment_date`, `appointment_time`) se mantienen como `DATE` y `TIME` sin zona horaria (manejadas vía `zoneinfo` en Python).
5. **Transacciones & Concurrencia**: `BEGIN IMMEDIATE` → `BEGIN ISOLATION LEVEL READ COMMITTED` + Locks de Transacción Consultivos (`pg_advisory_xact_lock`) por `(business_id, date)` para evitar lecturas fantasma (phantom reads) en slots no existentes + `SELECT ... FOR UPDATE` sobre filas existentes + Índice Único Parcial como defensa en profundidad.
6. **Placeholders**: Posicionales `%s` nativos de `psycopg3`. Se elimina cualquier reemplazo textual automático/ciego (`?` → `%s`) en runtime; cada query será auditada, modificada y verificada individualmente.
7. **Generación de IDs**: Reemplazo total de `cursor.lastrowid` por la cláusula nativa `INSERT ... RETURNING id`.
8. **FTS**: Migrado de FTS5 a `tsvector` + índice `GIN` nativo en PostgreSQL. Se documentan las diferencias de tokenización/stemming y se requiere suite de equivalencia funcional.
9. **Backups & Migración**: Distinción clara entre el ETL en Python (migración de datos de SQLite a PostgreSQL) y `pg_dump`/`pg_restore` (herramientas PostgreSQL para backup/restore continuo).
10. **Rollback**: Definición clara de la ventana de reversibilidad y la gestión de writes producidos en PostgreSQL post-cutover.

### B.2 Configuración de conexión y DSN (Punto 4)

- **DSN Recomendado**: `postgresql://user:password@host:5432/turnobot`
  - **Aclaración de Contexto**: `postgresql://` es el formato DSN estándar de `libpq` utilizado directamente por `psycopg3`.
  - **No mezclar**: `postgresql+psycopg://` es una sintaxis específica de dialectos ORM (como SQLAlchemy). Como TurnoGo utiliza `psycopg3` de forma directa sin ORM, la única URL oficial para la aplicación es `postgresql://`.
- **Pool de Conexiones**: `psycopg_pool.ConnectionPool` por proceso de aplicación Waitress.
  - Limits iniciales: `min_size=1`, `max_size=10`, `max_idle=5`, `max_lifetime=1800` (30 min).
  - Lifecycle: Inicializado al arrancar la aplicación (`init_app`), registrado en el contexto de Flask.
  - Checkout/Checkin: Administrado mediante context manager (`with pool.connection() as conn:`).
  - Cierre y Reorganización: `pool.close()` al detener el proceso. Reconexión automática ante caídas de red.
- **Nivel de Aislamiento**: `READ COMMITTED` (default de PostgreSQL).
- **Autocommit**: `FALSE` por defecto. El código controla explícitamente los `commit()` y `rollback()`.

## C. Modelo de datos y clasificaciones

### C.1 Clasificación de entidades (Global vs Tenant-Scoped) (Punto 6)

No todas las tablas ni claves foráneas de TurnoGo pertenecen al ámbito tenant de la misma manera. Se clasifica rigurosamente el modelo para preparar el terreno hacia una futura Row-Level Security (RLS) sin asumir que todas requieren `business_id` directo:

#### 1. GLOBAL (Sin `business_id`)
Entidades de la plataforma que existen de forma independiente a cualquier negocio específico:
- `users`: Cuentas globales de usuarios (propietarios, administradores, empleados, clientes).
- `roles`: Catálogo global de roles del sistema (`owner`, `admin`, `staff`, `customer`).
- `platform_users`: Usuarios administradores del panel super-admin TurnoGo.
- `platform_sessions`: Sesiones activas de usuarios de plataforma.
- `businesses`: Catálogo global de negocios/tenants registrados.

#### 2. LINK / JUNCTION (Relación Global ↔ Tenant)
Tablas pivote o de vinculación que conectan entidades globales con tenants:
- `business_users`: Conecta `user_id` (global) con `business_id` (tenant) y su `role_id`. Tiene `business_id`, pero actúa como mapping N:M entre usuario global y negocio.
- `invitations`: Invitaciones enviadas a usuarios para unirse a un `business_id`. Contiene `business_id` y `invited_by_user_id`.
- `sessions`: Sesión web vinculada a un `user_id` global con un `current_business_id` contextual activo.

#### 3. TENANT-SCOPED DIRECT (Pertenencia estricta a un `business_id`)
Entidades que pertenecen exclusivamente a un tenant. Requieren `business_id NOT NULL REFERENCES businesses(id)` y serán el blanco principal de políticas RLS futuras:
- `business_settings` (Configuración 1:1 por negocio, `UNIQUE(business_id)`)
- `weekly_schedules` (Horarios semanales del negocio)
- `services` (Catálogo de servicios del negocio)
- `resources` (Recursos / barberos / profesionales del negocio)
- `appointments` (Turnos reservados en el negocio)
- `notification_log` (Log de notificaciones enviadas por turnos del negocio)
- `loyalty_settings` (Configuración del programa de puntos del negocio)
- `loyalty_accounts` (Cuentas de fidelización de clientes del negocio)
- `points_ledger` (Libro mayor de puntos ganados/canjeados)
- `rewards` (Premios configurados por el negocio)
- `redemptions` (Canjes de premios realizados en el negocio)
- `retention_actions` (Acciones de retención de clientes del negocio)
- `business_knowledge` (Base de conocimiento IA del negocio)
- `conversation_sessions` (Sesiones del asistente IA por negocio)
- `conversation_messages` (Mensajes del chat IA vinculados a una sesión del negocio)
- `conversation_analytics` (Analíticas de uso del chat IA por negocio)

#### 4. INDIRECT / MIXED (Relaciones especiales)
- `password_reset_tokens`: Vinculado a `user_id` (global), pero puede contener `business_id` opcional si la solicitud se originó en el portal de un negocio.
- `audit_log`: Log de auditoría global de plataforma. Contiene `actor_id`, `target_type`, `target_id`, y puede registrar eventos globales de plataforma o eventos específicos de negocio.

## D. Mapping de tipos y análisis de evidencias

### D.1 Datetime, UTC y Zonas Horarias (Punto 1)

1. **Comportamiento Real de SQLite**:
   - `datetime('now')` y `CURRENT_TIMESTAMP` en SQLite **NO** generan la hora local del servidor. Generan de forma nativa una cadena de texto en formato ISO-8601 en **UTC** (`YYYY-MM-DD HH:MM:SS`).
2. **Timestamps SQLite vs Calculados en Python**:
   - Timestamps de auditoría/sistema (`created_at`, `updated_at`, `claimed_at`, `sent_at`, `expires_at`): Generados por SQLite via `CURRENT_TIMESTAMP` / `datetime('now')` o en Python via `datetime.now(tz=UTC)`. Todos están conceptualmente en UTC.
   - Fechas/horas de negocio (`appointment_date`, `appointment_time`, `appointment_end`, horarios de atención): Son valores "wall-clock" ingresados por el usuario para la zona horaria del negocio (`America/Argentina/Buenos_Aires`). Se almacenan como `DATE` y `TIME` sin información de zona horaria. Python las interpreta en la timezone del negocio usando `zoneinfo.ZoneInfo`.
3. **Estrategia Inequívoca de Transformación de Históricos**:
   - Los timestamps históricos en SQLite (`'2026-09-17 14:30:00'`) provienen de `datetime('now')` en UTC.
   - Cadena de transformación:
     `SQLite TEXT ("YYYY-MM-DD HH:MM:SS")` → `Python datetime.fromisoformat() con tz=UTC` → `PostgreSQL TIMESTAMPTZ`.
   - Para valores heredados vacíos (`created_at = ''` en registros legacy previos a migración 013), el script ETL asignará el timestamp de la migración o la fecha de creación del negocio.
4. **Reemplazo de SQL**:
   - SQL SQLite: `datetime('now')` / `CURRENT_TIMESTAMP` → PostgreSQL: `NOW()`.

### D.2 Evidence-based Audit: `services.price` / Unidad Monetaria (Punto 7)

Se realizó una auditoría profunda sobre el código fuente y la suite de tests para determinar la unidad monetaria real de `services.price`:

1. **Evidencia en Esquema SQLite**:
   - `services.price` está definido como `REAL NOT NULL DEFAULT 0`.
   - Datos semilla (`001_initial.sql`): `10000` (Corte), `15000` (Corte + barba), `7000` (Barba).
2. **Evidencia en Formularios y Rutas Admin**:
   - En `routes/admin.py:125`: `price = float(price_raw)`.
   - En `templates/admin.html:647`: `<input type="number" name="price" min="0" step="0.01" required>`. El atributo `step="0.01"` demuestra que la interfaz soporta centavos explícitamente.
3. **Evidencia en Presentación al Usuario**:
   - En `services/ai.py:512`: `f"- {service['name']}: ${service['price']:,.0f}".replace(",", ".")` (formatea $10.000).
   - En `templates/landing.html:295` y `templates/reservar_wizard.html:386`: `<span>$${ service.price }}</span>`. Se antepone el signo `$` directamente al número almacenado.
4. **Evidencia de Operaciones Matemáticas**:
   - **No existe división por 100 ni conversión de centavos** en ningún lugar del backend Python ni del frontend JS. El valor $10000 representa 10.000 pesos argentinos (ARS), monto habitual para servicios de barbería en Argentina.
5. **Conclusión y Tipo PostgreSQL Definido**:
   - La hipótesis de que los valores estaban en centavos queda descartada por evidencia empírica.
   - El tipo oficial en PostgreSQL para `services.price` será **`NUMERIC(10,2)`**, garantizando representación exacta de montos en pesos con soporte de hasta 2 decimales para centavos.

## E. Estrategia de conexiones, pool y placeholders

### E.1 Driver y Connection Pool (Punto 8)

- **Librería**: `psycopg` (versión 3) con `psycopg_pool`.
- **Pool por Proceso**: Cada worker de Waitress/Flask mantiene su propia instancia de `ConnectionPool` aislada.
- **Configuración de Pool**:
  - `min_size = 1`: Mantiene al menos 1 conexión caliente.
  - `max_size = 10`: Límite máximo de conexiones concurrentes por worker.
  - `max_idle = 300`: Tiempo máximo en segundos para cerrar conexiones ociosas.
  - `timeout = 10.0`: Segundos de espera para obtener una conexión libre antes de lanzar `PoolTimeout`.
- **Patrón de Uso en Código**:
  ```python
  # database/database.py
  from psycopg_pool import ConnectionPool

  pool = ConnectionPool(conninfo=DATABASE_URL, min_size=1, max_size=10, open=False)


  def get_connection():
      return pool.connection()
  ```
  Los cursores retornarán dicts configurando `row_factory = dict_row`, manteniendo la compatibilidad de acceso por clave `row["columna"]` que se usaba con `sqlite3.Row`.

### E.2 Eliminación de Placeholders Ciegas `?` → `%s` (Punto 2)

1. **Decisión de Diseño**: PostgreSQL / `psycopg3` utiliza `%s` como placeholder de parámetros posicionales.
2. **Rechazo de Helpers Runtime Genéricos**:
   - **Queda terminantemente prohibido utilizar un helper de texto automático en runtime** (ej: `sql.replace('?', '%s')`).
   - *Razón técnica*: Un reemplazo ciego altera cadenas SQL que contengan el carácter `'?'` como texto literal (por ejemplo, en búsquedas de texto, JSON, o consultas de la base de conocimiento IA como `WHERE question LIKE '%?'`).
3. **Estrategia de Migración de Queries**:
   - **Audición y Reemplazo Manual**: Cada sentencia SQL en `database/database.py`, `services/*.py` y `routes/*.py` será revisada y modificada directamente en el código fuente durante la Fase 4F.
   - **Queries Dinámicas**: Las consultas que construyen cláusulas `IN (?, ?, ?)` dinámicamente deberán armarse explícitamente con `','.join(['%s'] * len(items))`.
   - **Validación**: La suite de unit tests e integración verificará sintácticamente cada query contra PostgreSQL.

---

### E.3 Reemplazo de `cursor.lastrowid` por `RETURNING id` (Punto 5)

1. **Deficiencia de `lastrowid` en PostgreSQL**:
   `cursor.lastrowid` en PostgreSQL depende de que la tabla tenga una secuencia asociada detectada por el driver driver-side. No es el mecanismo idiomatico ni 100% confiable en inserts complejos o masivos.
2. **Estrategia Elegida**: Reemplazo total por **`INSERT ... RETURNING id`**.
3. **Ejemplo de Modificación**:
   ```python
   # SQLite anterior:
   cursor = connection.execute("INSERT INTO appointments (...) VALUES (...)", params)
   appointment_id = cursor.lastrowid

   # PostgreSQL propuesto (Fase 4F):
   cursor = connection.execute("INSERT INTO appointments (...) VALUES (...) RETURNING id", params)
   appointment_id = cursor.fetchone()["id"]
   ```
4. **Puntos de Impacto en el Código**:
   - `database/database.py`: `create_business`, `create_user`, `create_role`, `create_service`, `create_resource`, `create_loyalty_account`, `create_reward`, `create_knowledge_item`, `create_platform_user`.
   - `services/appointments.py`: `create_appointment`.
   - `services/conversations.py`, `services/notifications.py`, `services/platform.py`.
5. **Tests Necesarios**: Unit tests para cada función `create_*` verificando que retornan un ID entero válido mayor a 0.

## F. Estrategia de concurrencia en reservas (Punto 3 - CRÍTICO)

### F.1 Desmitificación: Por qué `SELECT FOR UPDATE` + Unique Index NO es suficiente

Relying solely on `SELECT FOR UPDATE` + Unique Partial Index fails in real concurrent scenarios:

1. **Filas Fantasma / Inexistentes (Phantom Reads)**:
   Si dos transacciones (TX1 y TX2) intentan reservar el **mismo slot que actualmente está vacío**:
   - TX1 ejecuta `SELECT id FROM appointments WHERE ... FOR UPDATE`. Como el turno no existe, la consulta devuelve **0 filas**. `FOR UPDATE` **NO bloquea nada**.
   - TX2 ejecuta la misma consulta antes de que TX1 inserte. También devuelve **0 filas** y **NO bloquea nada**.
   - Ambas transacciones concluyen que el turno está libre y proceden a ejecutar `INSERT`.
2. **Límite del Índice Único Parcial**:
   - El índice único está definido sobre `(business_id, appointment_date, appointment_time, COALESCE(resource_id, -1))`.
   - Si TX1 y TX2 intentan reservar a la **misma hora exacta** (ej. 10:00) para el mismo recurso, el índice único detendrá a la segunda con un `IntegrityError`.
   - **PERO** si TX1 solicita **10:00 a 11:00** y TX2 solicita **10:30 a 11:30** (solapamiento parcial de intervalo), las horas de inicio (`10:00` vs `10:30`) son **distintas**. El índice único **NO detecta el conflicto**. Ambas transacciones insertarían exitosamente, produciendo una **doble reserva**.

---

### F.2 Matriz de Escenarios de Concurrencia y Mecanismos de Exclusión

| Escenario de Conflicto | Descripción | Mecanismo que Garantiza Exclusión |
| :--- | :--- | :--- |
| **A. Hora de inicio idéntica** | 2 reservas a las 10:00 para el mismo recurso/negocio. | Unique Partial Index `(business_id, date, time, resource)` + Lock de Transacción. |
| **B. Intervalo parcialmente solapado** | Reserva 10:00-11:00 vs Reserva 10:30-11:30. | **`pg_advisory_xact_lock` por negocio/fecha/recurso** + Consulta de solapamiento. |
| **C. Filas que ya existen** | Reserva sobre un slot donde ya hay un turno `confirmed`. | `SELECT ... FOR UPDATE` sobre la fila existente bloquea y cancela la 2ª TX. |
| **D. Filas que todavía no existen** | 2 reservas simultáneas sobre un slot libre (Phantom read). | **`pg_advisory_xact_lock`** serializa los cheques e inserts para ese negocio/fecha. |
| **E. Reserva con resource_id** | Reserva asignada a un barbero/recurso específico. | Advisory lock contextualizado al `resource_id`. |
| **F. Reserva sin resource_id (Global)** | Reserva a nivel negocio sin recurso asignado. | Advisory lock a nivel `business_id` + fecha. |
| **G. Reserva global vs con recurso** | Regla de negocio cuando coexisten turnos globales y por recurso. | **`DECISIÓN DE NEGOCIO PENDIENTE`** (Ver F.4). |

---

### F.3 Comparativa de Estrategias Técnicas

1. **Row Locking (`SELECT FOR UPDATE`)**: Bloquea filas existentes. Ineficaz ante filas que no existen (phantom reads).
2. **Unique Partial Index**: Altamente eficiente para duplicados de hora exacta. Incapaz de validar solapamientos de intervalos de duración variable.
3. **Exclusion Constraints (`EXCLUDE USING GIST`)**:
   - Utiliza la extensión `btree_gist` y rangos `tsrange`.
   - *Evaluación*: Aunque soporta solapamiento de rangos (`&&`), presenta alta complejidad para manejar la condición `resource_id IS NULL` (reserva global) frente a `resource_id = X` dentro de la misma regla de exclusión SQL.
4. **Advisory Locks Nativos (`pg_advisory_xact_lock`) (ESTRATEGIA ELEGIDA PARA TURNOGO)**:
   - Se ejecuta un lock de transacción basado en el hash del negocio, fecha y recurso:
     `SELECT pg_advisory_xact_lock(hashtext(business_id || ':' || appointment_date || ':' || COALESCE(resource_id, 0)));`
   - *Ventajas*:
     - Se libera automáticamente al finalizar la transacción (`COMMIT` o `ROLLBACK`).
     - Previene 100% las lecturas fantasma sin bloquear otras fechas ni otros negocios.
     - No requiere extensiones adicionales como `btree_gist`.
     - Permite que la segunda transacción lea el turno recién insertado por la primera una vez desbloqueada y decline la reserva por "occupied".

---

### F.4 Regla de Negocio Ambigua: Global vs Recurso

> [!IMPORTANT]
> **DECISIÓN DE NEGOCIO PENDIENTE**
> En el código actual (`services/appointments.py:554`), si se reserva un turno con `resource_id`, el filtro de solapamiento busca turnos que tengan ese `resource_id` O `resource_id IS NULL`. Pero si se reserva un turno sin `resource_id` (reserva global), busca solapamientos con **todos** los turnos del negocio.
> *Ambigüedad*: ¿Un turno "global" (sin recurso) bloquea a todos los barberos del local o significa simplemente que el cliente no eligió barbero y el sistema debe asignarle uno libre?
> Esta regla no se modificará ni inventará en el diseño. Se mantendrá la consulta SQL actual envuelta en el Advisory Lock hasta que Negocio defina la regla final.

## G. Estrategia de Full-Text Search (FTS) (Punto 10)

### G.1 Análisis de Equivalencia FTS5 (SQLite) vs `tsvector` + GIN (PostgreSQL)

FTS5 en SQLite y `tsvector` en PostgreSQL **NO son 100% idénticos fuera de la caja**. Se documentan las diferencias potenciales:

| Característica | SQLite FTS5 (Actual) | PostgreSQL `tsvector` (Propuesto) | Impacto / Mitigación |
| :--- | :--- | :--- | :--- |
| **Tokenizer / Stemming** | Tokenizer `unicode61` (indexa palabras exactas sin lematización por defecto). | Diccionario `'spanish'` de Snowball (lematiza palabras: "cortes" → "cort"). | PostgreSQL encuentra coincidencias morfológicas (mejora la búsqueda). |
| **Stopwords** | No filtra palabras vacías por defecto. | Filtra palabras comunes en español ("de", "la", "con"). | Previene falsos positivos en palabras irrelevantes. |
| **Búsqueda Parcial** | Sintaxis `palabra*`. | Sintaxis `palabra:*` via `to_tsquery`. | Se adaptará la construcción de la query en Python. |
| **Ranking** | Función `rank` (algoritmo Okapi BM25). | Función `ts_rank` / `ts_rank_cd` (frecuencia y cobertura). | Equivalencia funcional en orden de relevancia. |
| **Acentos / Diacríticos** | `remove_diacritics=1`. | Extensión `unaccent` o configuración de diccionario. | Se recomienda activar extensión `unaccent` en PostgreSQL. |

### G.2 Implementación en PostgreSQL

La columna calculada `document_tsearch` en `business_knowledge` se actualiza automáticamente. La función `search_knowledge_scoped` en `services/knowledge.py` se actualizará a:

```sql
SELECT id, question, answer, tags,
       ts_rank(document_tsearch, websearch_to_tsquery('spanish', %s)) AS rank
FROM business_knowledge
WHERE business_id = %s
  AND active = TRUE
  AND document_tsearch @@ websearch_to_tsquery('spanish', %s)
ORDER BY rank DESC
LIMIT %s;
```

## H. Estrategia de migración de datos ETL (Punto 9)

### H.1 Aclaración Tooling PostgreSQL vs SQLite

> [!NOTE]
> `pg_dump` y `pg_restore` son herramientas nativas de PostgreSQL para backups y restauros entre instancias PostgreSQL. **NO son herramientas de extracción de SQLite**.
> La migración de SQLite a PostgreSQL se realizará mediante un script **Python ETL dedicado** (`scripts/migrate_to_postgres.py`).

### H.2 Pipeline del Script Python ETL

1. **Pre-flight Check**:
   - Verificar `schema_version == 022` en SQLite.
   - Ejecutar `PRAGMA foreign_key_check` en SQLite (0 errores).
2. **Extracción (Extract)**:
   - Lectura ordenada por dependencias FK (negocios → usuarios → servicios/recursos → turnos → logs).
3. **Transformación (Transform)**:
   - Mapeo de `0/1` a `BOOLEAN` (`True`/`False`).
   - Conversión de ISO strings UTC a objetos `datetime` con `tz=UTC`.
   - Manejo de strings vacíos en `created_at` → asignación de `NOW()`.
   - Limpieza de nulos e integridad de tipos.
4. **Carga (Load)**:
   - Uso de `cursor.copy()` de `psycopg3` para inserción masiva a alta velocidad.
   - Preservación estricta de PKs (`INSERT INTO table OVERRIDING SYSTEM VALUE`).
5. **Reinicio de Secuencias (Post-load)**:
   ```sql
   SELECT setval(pg_get_serial_sequence('businesses', 'id'), COALESCE(MAX(id), 1)) FROM businesses;
   SELECT setval(pg_get_serial_sequence('users', 'id'), COALESCE(MAX(id), 1)) FROM users;
   -- Repetir para todas las tablas con PK autoincremental
   ```
6. **Validación de Integridad**:
   - Conteo estricto de filas por tabla (`COUNT(*)` SQLite vs PostgreSQL).
   - Verificación de checksums/hashes en columnas clave (ej. suma total de IDs, hashes de contraseñas).
   - Verificación de restricciones de FK en PostgreSQL.
7. **Rollback del ETL**: Si la validación falla, se ejecuta `DROP SCHEMA public CASCADE; CREATE SCHEMA public;` en PostgreSQL. SQLite permanece 100% intacto sin modificaciones.

## I. Estrategia de Rollback y Ventana de Reversibilidad (Punto 11)

NO se debe asumir "volver a SQLite" como un rollback universal sin analizar la pérdida de datos. Se establecen 3 ventanas de reversibilidad:

```
[ Ventana 1: Pre-cutover ] ──▶ [ Ventana 2: Cutover (0-15m) ] ──▶ [ Ventana 3: Producción Activa ]
   Reversibilidad: 100%           Reversibilidad: 100%               Reversibilidad: Condicionada
   Pérdida de datos: 0             Pérdida de datos: 0                Pérdida de datos: Writes en PG
```

1. **Ventana 1: Durante la Mantenimiento (Pre-Cutover)**:
   - *Estado*: ETL en progreso o validación post-ETL fallida antes de abrir el tráfico.
   - *Acción*: Cancelar migración, mantener Nginx/Waitress apuntando a SQLite.
   - *Pérdida de datos*: **0%**.
2. **Ventana 2: Inmediatamente Post-Cutover (0 a 15 minutos)**:
   - *Estado*: Tráfico abierto, pero se detecta un error crítico de la app antes de registrar escrituras de usuarios.
   - *Acción*: Detener Waitress, apuntar `DATABASE_URL` de nuevo a SQLite, reiniciar Waitress.
   - *Pérdida de datos*: **0%**.
3. **Ventana 3: Producción Activa (Post-15 minutos con escrituras en PostgreSQL)**:
   - *Estado*: Han ingresado reservas, usuarios o canjes de puntos reales en PostgreSQL.
   - *Conflicto*: Volver al archivo SQLite backup **perderá permanentemente** todas las escrituras realizadas en PostgreSQL durante el tiempo de operación.
   - *Criterio de Abortar / Decisión*:
     - Si el error rate en PostgreSQL es > 5% en los primeros 15 min → Rollback a SQLite inmediato (se aceptan perder escrituras mínimas).
     - Si el problema ocurre horas después → **NO se realiza rollback a SQLite**. Se aplica un hotfix sobre PostgreSQL en caliente o se ejecuta un ETL inverso (PG → SQLite) antes de restaurar.
4. **Preservación de Datos**: Durante las primeras 24 horas post-migración, se tomarán dumps de PostgreSQL (`pg_dump`) cada 15 minutos.
