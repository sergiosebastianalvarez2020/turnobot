### Problemas identificados en el flujo cliente

1. **Sin notificaciones de email**: el cliente nunca recibe confirmación ni recordatorio (SMTP no configurado en producción)
2. **Sin recordatorio visual post-reserva**: el wizard redirige a `window.location.href = apiBase + '/?reserva=ok'` pero la landing page no tiene lógica para mostrar "Reserva exitosa" (no hay query param `?reserva=ok` handler en `index()`)
3. **Sin manejo de errores de `create_appointment` en el wizard POST**: si la fecha/hora está ocupada, `create_appointment` returns `{"success": False, "reason": "occupied"}` → el wizard POST returns 400 con el mensaje. **Pero** `landing.js` no muestra este error correctamente — el manejo de errores del POST solo revisa `data.success` y muestra `data.error` o un mensaje genérico.

### 8.4 Análisis de la amenaza del prompt injection

**Estado: LOW RIESGO**

- User input se pasa directamente a Gemini como contenido de mensaje, no como system prompt
- System prompt está separado (`system_instruction` parameter)
- Conversation messages son persistidas a DB antes de la llamada (audit trail)
- No hay sanitización explícita, pero la estructura de system prompt separado mitiga la mayoría de riesgos

## 9. Base de datos

### 9.1 Schema

- **Motor**: SQLite 3 (WAL mode, FKs ON, busy_timeout 10s)
- **22 tablas** + 2 tablas de control (`schema_version`, `migration_log`) + FTS5 virtual (`business_knowledge_fts`)
- **Migraciones**: `migrations/001_initial.sql` → `022_unique_appointment_slot.sql`
- **Versión en OCI**: migración 022 aplicada (verified via schema inspection)
- **Tamaño OCI**: 385 KB (1 negocio, 21 turnos, 1 usuario)

### 9.2 Concurrency / double-booking

Tres capas de defensa:
1. **Transacción**: `BEGIN IMMEDIATE` en `create_appointment` (line 571) — serializa writes
2. **Índice único parcial**: `unique_confirmed_appointment_slot` sobre `(business_id, appointment_date, appointment_time, COALESCE(resource_id, -1)) WHERE status='confirmed'` — guarda DB-level
3. **Pattern atómico**: `claim_notification_scoped`, `consume_invitation_atomically`, `consume_password_reset_token` usan `BEGIN IMMEDIATE` + UPDATE condicional + `rowcount` check

✅ Tests de concurrencia: `test_security_concurrency.py` — 3 tests (1 flaky en Windows, documentado)

### 9.3 Multi-tenancy en DB

✅ **Sólido.** Tenant derivado de URL slug (`resolve_business`), `business_id` pasado a toda query vía funciones `_scoped`. Funciones legacy no-scoped (`get_all_services`, `update_business_settings`) están marcadas como "no ganar nuevos llamadores".

## 17. Performance

| Área | Evaluación |
|---|---|
| **SQLite single-writer** | ⚠️ `BEGIN IMMEDIATE` serializa todos los writes. Bien para baja/moderada concurrencia. No escala horizontalmente. |
| **Queries principales** | ✅ Indexados correctamente (business_id, appointment_date/status, etc.) |
| **AI latency** | ✅ 15s timeout, retry con backoff |
| **Logging** | ✅ No bloqueante (logging asíncrono via `QueueHandler`) |
| **Generación de calendario** | ✅ Cliente-side (JS), no server-side |
| **Carga de servicios** | ✅ Caché implícito por request scope |

**Cuello de botella principal:** SQLite como único writer. En una carga de +100 negocios concurrentes reservando simultáneamente, el `busy_timeout` de 10s puede agotarse.

## 25. Responder las preguntas clave

### ¿Qué puede hacer TurnoGo HOY?

Landings pages con branding, wizard de reserva de 4 pasos con validación completa, chat con IA (consulta disponibilidad, reserva, busca turnos), gestion de turnos via token, panel admin completo (servicios, horarios, turnos, usuarios, conocimiento, IA, fidelización, recursos), superadmin para crear/aprobar negocios, sistema de backups verificado. **Pero**: no envía emails (SMTP no configurado), no tiene HTTPS, y hay 5 bugs críticos en la IA.

### ¿Qué necesita para el primer cliente piloto?

1. Deploy actualizado a OCI (d25c227)
2. HTTPS configurado (certificado + redirect)
3. SMTP configurado y testeado
4. Fix del bug `get_business_identity()` (crash garantizado en reservas vía chat)
5. Fix del flujo de cancelación/reprogramación vía chat AI

### ¿Qué necesita para venta?

Todo lo anterior +:
- Notificaciones de cancelación/reprogramación
- Fix de emails de confirmación vía AI (management_token)
- Dashboard de métricas
- Onboarding guiado
- README y documentación

### ¿Qué riesgos existen?

| Riesgo | Severidad |
|---|---|
| Sin HTTPS → credenciales expuestas en tránsito | 🔴 Crítico |
| Sin SMTP → clientes nunca reciben confirmación | 🔴 Crítico |
| AI crash en reserva via chat → mala UX | 🔴 Crítico |
| Rate limiting por-proceso → fácil de bypass | 🟠 Alto |
| Sin CSP → XSS si hay vulnerabilidad en template | 🟡 Medio |
| SQLite single-writer → lock en alta concurrencia | 🟡 Medio |

### ¿Qué podemos dejar para después?

- Migrar SQLite → PostgreSQL (para +100 negocios)
- Rate limiting distribuido (Redis)
- Gestión de clientes como entidad
- Métricas de negocio en dashboard
- CSP header (defensa en profundidad)
